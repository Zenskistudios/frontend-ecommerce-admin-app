# Stockroom Frontend — Code Walkthrough

This explains every file in the project as it currently stands: what it
does, why it's written that way, and the concept it's teaching. Read it next
to the actual files.

---

## 1. Config files (the boring-but-necessary layer)

### `package.json`
Lists what the project depends on and the commands you can run.
- `react`, `react-dom` — React itself
- `react-router-dom` — client-side routing (switching pages without a full
  page reload)
- `axios` — makes HTTP requests to the backend, nicer API than the browser's
  built-in `fetch`
- `tailwindcss` (v4) + `@tailwindcss/vite` — the CSS toolchain

`npm run dev` runs the `dev` script (`vite`), which starts a local server
that rebuilds instantly when you save a file.

**There's no `tailwind.config.js` or `postcss.config.js` anymore.** Tailwind
v4 removed the JS config file entirely — theme customization moved into CSS
itself (see `src/index.css` below), and the PostCSS pipeline got replaced by
a dedicated Vite plugin. That's a deliberate v4 decision, not something
missing from this project.

### `vite.config.js`
```js
import tailwindcss from '@tailwindcss/vite'

export default defineConfig({
  plugins: [react(), tailwindcss()],
  server: { port: 5173 },
})
```
Two plugins: `react()` handles JSX compilation, `tailwindcss()` handles
scanning your files for class names and generating the matching CSS. In v3
this scanning was PostCSS's job, configured via `content: [...]` in
`tailwind.config.js`. In v4 it's automatic — the Vite plugin watches your
source files directly, no config array needed.

### `index.html`
The one real HTML file in the whole app. Note two things:
1. `<div id="root"></div>` — React mounts your entire app inside this single
   div. Everything else on the page is generated by JavaScript.
2. `<script type="module" src="/src/main.jsx">` — this is what kicks
   everything off.

### `src/index.css` — the theme now lives here
```css
@import "tailwindcss";

@theme {
  --color-ink: #161616;
  --color-stock-navy: #1B2340;
  --color-stock-navy-light: #28325B;
  --color-amber: #E8A23D;
  --color-amber-dark: #C9822A;
  --color-ok: #2E7D5B;
  --color-low: #C9822A;
  --color-out: #C1443D;

  --font-display: "Space Grotesk", sans-serif;
  --font-body: "Inter", sans-serif;

  --radius-sm: 4px;
}
```
This is the v4 replacement for the old `tailwind.config.js` `theme.extend`
block. Every variable inside `@theme` automatically becomes a set of
utility classes — define `--color-amber` and you get `bg-amber`,
`text-amber`, `border-amber`, all for free, no `plugins` array involved.

**The naming rule that matters:** CSS custom properties don't support nested
objects the way a JS config could (`stock: { navy, navyLight }` isn't valid
CSS). Everything has to be flattened into one dash-separated name —
`--color-stock-navy-light` — which is why the utility class is
`bg-stock-navy-light`, not the old camelCase `bg-stock-navyLight`. If you
ever add a new token here, the pattern is: `--color-<name>` in CSS becomes
`bg-<name>` / `text-<name>` / etc. as a class, always kebab-case.

The `@layer base { html { ... } }` block at the bottom still works exactly
like it did in v3 — that part of Tailwind's API didn't change.

## 2. The boot sequence: `main.jsx` → `App.jsx` → `router/index.jsx`

This is the part worth understanding really well, because "where does
rendering start" trips people up constantly.

### `src/main.jsx` — the actual entry point
```jsx
ReactDOM.createRoot(document.getElementById('root')).render(
  <AuthProvider>
    <App />
  </AuthProvider>
)
```
This is the *only* place React attaches itself to the real DOM. It says:
"find the `#root` div, and render `<AuthProvider><App /></AuthProvider>`
inside it." `AuthProvider` wraps the whole app so that *any* component,
anywhere, can ask "is someone logged in?" — more on that below.

Notice there's no `<BrowserRouter>` here. That's because `App.jsx` now uses
`createBrowserRouter`, which brings its own routing context — wrapping in
`<BrowserRouter>` as well would be redundant (and actually breaks things,
since you'd have two routers).

### `src/App.jsx`
```jsx
import { RouterProvider } from 'react-router-dom'
import router from './router/index.jsx'

export default function App() {
  return <RouterProvider router={router} />
}
```
`App` doesn't do much on its own — it just hands control to the router.
`RouterProvider` reads the route config from `router/index.jsx` and renders
whichever page matches the current URL.

### `src/router/index.jsx` — the route table
```jsx
const router = createBrowserRouter([
  { path: '/login', element: <Login /> },
  {
    path: '/products',
    element: <ProtectedRoute><ProductList /></ProtectedRoute>,
  },
  {
    path: '/products/:id/edit',
    element: <ProtectedRoute><ProductForm /></ProtectedRoute>,
  },
  { path: '/', element: <Navigate to="/products" replace /> },
  { path: '*', element: <Navigate to="/products" replace /> },
])
```
This is a plain JS array of `{ path, element }` objects — that's the whole
route table for the app. `:id` is a **URL parameter**, a placeholder: if
someone visits `/products/42/edit`, this route matches and `"42"` becomes
available inside `ProductForm` via the `useParams()` hook (see below).

This lives in its own file, and specifically as `.jsx` rather than `.js`,
because it contains JSX (`<Login />` etc.) — Vite's default loader only
parses JSX syntax in `.jsx`/`.tsx` files.

Why this array-of-objects style instead of the `<Routes><Route>` JSX tree
you might see in older tutorials? Functionally identical for what this
project uses — the difference only matters if you later adopt route
`loader`/`action` functions (fetching data *before* a page renders, instead
of inside a `useEffect` after it mounts). Not needed yet, just
future-proofing.

## 3. Auth: how "being logged in" is tracked

### `src/context/AuthContext.jsx`
This is **React Context** — a way to share a piece of state (here: "who's
logged in") with any component in the tree, without manually passing it
down as props through every layer.

```jsx
const AuthContext = createContext(null)

export function AuthProvider({ children }) {
  const [user, setUser] = useState(...)
  // ...
  return <AuthContext.Provider value={{ user, login, logout, isAuthenticated }}>
    {children}
  </AuthContext.Provider>
}

export function useAuth() {
  return useContext(AuthContext)
}
```

Think of it in two halves:
- **`AuthProvider`** is a box that holds the `user` state and exposes
  `login()` / `logout()` functions. You wrap the app in it once, in
  `main.jsx`.
- **`useAuth()`** is how any component *inside* that box reaches in and
  grabs `user`, `login`, `logout` — that's what `Sidebar.jsx` and
  `Login.jsx` are doing when they call `const { user, logout } = useAuth()`.

`login()` doesn't just set `user` in memory — it also writes to
`localStorage`:
```jsx
localStorage.setItem('authToken', token)
localStorage.setItem('authUser', JSON.stringify(user))
```
That's so a page refresh doesn't log you out. On load, `useState` runs its
initializer function once, which checks `localStorage` for a saved user:
```jsx
const [user, setUser] = useState(() => {
  const stored = localStorage.getItem('authUser')
  return stored ? JSON.parse(stored) : null
})
```

### `src/components/ProtectedRoute.jsx`
```jsx
export default function ProtectedRoute({ children }) {
  const { isAuthenticated } = useAuth()
  if (!isAuthenticated) return <Navigate to="/login" replace />
  return children
}
```
A **wrapper component**. It doesn't render any UI of its own — it either
renders whatever you passed as `children` (the real page), or redirects to
`/login`. This is why the router config wraps protected pages like:
```jsx
element: <ProtectedRoute><ProductList /></ProtectedRoute>
```
`ProductList` only ever renders if `isAuthenticated` is true.

## 4. Talking to the backend: the `services/` layer

This is the most important architectural decision in the project, so it
gets the most explanation.

### `src/services/api.js`
```js
const api = axios.create({ baseURL: BASE_URL, headers: {...} })
```
One shared axios instance, configured once, reused everywhere. Two
**interceptors** attached to it:

1. **Request interceptor** — runs before every outgoing request, attaches
   the saved auth token:
   ```js
   api.interceptors.request.use((config) => {
     const token = localStorage.getItem('authToken')
     if (token) config.headers.Authorization = `Bearer ${token}`
     return config
   })
   ```
   No individual page ever has to remember to attach the token — it happens
   automatically for every request made through `api`.

2. **Response interceptor** — runs on every response. If the backend ever
   returns `401 Unauthorized` (token missing/expired), it clears storage and
   bounces the user to `/login`, from one central place instead of
   duplicating that check in every page.

`MOCK_MODE` is a simple boolean:
```js
export const MOCK_MODE = import.meta.env.VITE_MOCK_MODE === 'true' || !import.meta.env.VITE_API_BASE_URL
```
True if you explicitly force it, or if you haven't set a backend URL at all.
Every service file checks this flag.

### `src/services/productService.js` and `authService.js`
Each exported function has the same shape:
```js
export async function getProducts() {
  if (MOCK_MODE) {
    await delay()
    return [...mockProducts]
  }
  const { data } = await api.get('/products')
  return data
}
```
**Why this matters:** every page (`ProductList`, `ProductForm`) calls
`getProducts()` / `createProduct()` / etc. without knowing or caring whether
it's hitting mock data or a real server. That's the whole point of having a
services layer instead of calling `axios.get(...)` directly inside your
components — when your backend is ready, you flip `MOCK_MODE` off (by
setting `VITE_API_BASE_URL`) and **zero component code changes.** The UI
was never coupled to *how* the data arrives.

The mock data itself just lives in a JS array (`let mockProducts = [...]`)
that the functions mutate directly — `uid()` generates a fake ID for new
items, `delay()` fakes network latency so loading states are visible while
you're building.

## 5. The pages

### `src/pages/Login.jsx`
Standard **controlled form** pattern:
```jsx
const [email, setEmail] = useState('')
<input value={email} onChange={(e) => setEmail(e.target.value)} />
```
React state is the single source of truth for the input's value — the DOM
input doesn't hold its own value independently. Submitting calls
`login(email, password)` from `useAuth()`, and on success navigates to
wherever the user was trying to go before being bounced to `/login`:
```jsx
const from = location.state?.from?.pathname || '/products'
navigate(from, { replace: true })
```
(`ProtectedRoute` doesn't currently pass that `state`, so `from` will always
fall back to `/products` for now — worth wiring up if you want "redirect
back to the page I originally tried to visit" behavior.)

### `src/pages/ProductList.jsx`
Loads data once on mount:
```jsx
useEffect(() => {
  loadProducts()
}, [])
```
Empty dependency array `[]` means "run this once, right after the first
render" — the standard pattern for "fetch data when this page opens."

Delete uses a **two-step confirm** instead of a browser `confirm()` popup:
```jsx
const [pendingDeleteId, setPendingDeleteId] = useState(null)
```
Clicking "Delete" sets `pendingDeleteId` to that product's id, which swaps
the button for "Confirm / Cancel" *only on that row* — because the check is
`pendingDeleteId === product.id`, not a single global boolean.

### `src/pages/ProductForm.jsx`
The one component handling **both** create and edit:
```jsx
const { id } = useParams()
const isEditing = Boolean(id)
```
If the URL is `/products/new`, there's no `:id` param, so `id` is
`undefined` and `isEditing` is `false`. If it's `/products/42/edit`, `id` is
`"42"` and `isEditing` is `true`. Everything downstream branches on that one
boolean — whether to fetch existing data on mount, and whether to call
`createProduct()` or `updateProduct()` on submit.

Validation is a plain function, not a library:
```js
function validate(form) {
  const errors = {}
  if (!form.name.trim()) errors.name = 'Product name is required.'
  if (form.price === '' || Number(form.price) <= 0) errors.price = '...'
  return errors
}
```
It mirrors the exact rules from your Task 1 spec, so bad data never reaches
the API call in the first place. `handleSubmit` runs this, and only
proceeds if `Object.keys(validationErrors).length === 0`.

## 6. Small reusable components

### `src/components/Sidebar.jsx`
Uses `NavLink` (not `Link`) specifically because `NavLink` knows whether
its own route is currently active, so you can style it differently:
```jsx
const linkClasses = ({ isActive }) =>
  `... ${isActive ? 'bg-amber text-stock-navy' : 'text-white/70 ...'}`
```

### `src/components/StockBadge.jsx`
Pure presentational logic — takes a number, decides a color/label:
```jsx
if (quantity === 0) { tone = out; label = 'Out of stock' }
else if (quantity <= 5) { tone = low; label = `${quantity} left` }
```
No state, no side effects — just props in, JSX out. This is the simplest
kind of component to write and test.

### `src/components/MockModeBanner.jsx`
```jsx
if (!MOCK_MODE) return null
```
Returning `null` from a component means "render nothing." This is how you
conditionally show/hide entire pieces of UI in React — there's no separate
`display: none` mechanism needed at the component level.

## A note on the Tailwind v4 class-name gotcha

Worth calling out explicitly since it caused a real bug during this
project: renaming a `@theme` variable doesn't cause a build error if a
class still references the old name — it just silently stops generating
that CSS. When `stock.navyLight` (v3, camelCase) became
`--color-stock-navy-light` (v4, kebab-case), three files were still writing
`hover:bg-stock-navyLight`, and the build succeeded anyway with that hover
state doing nothing. After any `@theme` rename, grep the codebase for the
old token name before trusting a green build.

## Where to go next

If you want to build muscle memory rather than just reading, try:
1. Add a `Category` filter dropdown to `ProductList` — good practice with
   local component state and `.filter()`.
2. Wire `ProtectedRoute` to actually pass `state={{ from: location }}` so
   login redirects back to the page you originally wanted.
3. Swap `MOCK_MODE` off against a real backend once yours has a `/products`
   route, and watch the interceptor in `api.js` attach the token for you.
